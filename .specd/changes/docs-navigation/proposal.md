# Proposal

## Problem
The documentation is accurate enough to pass the mechanical release gates, but
it is not maintained as one coherent reader experience. The root README and
docs index repeat navigation and workflow material, while the nine hand-written
pages vary in tone, density, assumed knowledge, source-code detail, and how
they explain operational limits. Passing link and generated-document checks
does not prove that examples still match the current binary or that a developer
can judge whether specd is suitable for production use.

## Outcome
The root README and every hand-written page under `docs/` use one concise,
developer-friendly voice, have a clear audience and next step, and agree with
the current command registry, source, tests, security policy, and release
decision. Production guidance states the supported platform, proven base-loop
boundary, experimental production profile, and advisory host assurance without
overstating them.

## Scope
Review and revise `README.md`, `docs/README.md`, `docs/getting-started.md`,
`docs/concepts.md`, `docs/the-loop.md`, `docs/approval-and-evidence.md`,
`docs/agent-setup.md`, `docs/layout.md`, `docs/troubleshooting.md`, and
`docs/contributing.md`. Remove unnecessary repetition, normalize terminology
and voice, validate examples and claims against current repository facts, and
make navigation explicit for evaluators, users, agent integrators, and
contributors. Review generated `docs/operations.md` for registry parity but do
not hand-edit it.

## Non-goals
Changing product behavior, operation metadata, release claims, security policy,
or the generated bytes of `docs/operations.md`; renaming or splitting pages;
adding a documentation framework; or claiming production assurance beyond the
evidence in `release/release-decision.md`.
