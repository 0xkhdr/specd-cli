# The `.specd` layout

This page shows what specd writes, who owns each file, and what you may edit.

The short version: **Markdown is yours, everything else is the harness's.**

## The tree

```text
your-project/
  AGENTS.md               generated agent guidance; managed region + your notes
  .specd/
    .gitignore              managed; ignores the lock files below
    .root.lock              runtime only
    .records.lock           runtime only
    history.jsonl           append-only lifecycle history
    evidence.jsonl          append-only verification evidence
    specs/
      <capability>/
        spec.md             accepted truth, written by sync
    changes/
      <change>/
        .lock               runtime only
        state.json          harness-owned lifecycle state
        proposal.md         authored
        design.md           authored
        tasks.md            authored
        specs/
          <capability>/
            spec.md         authored delta spec
    archive/
      <YYYY-MM-DD>-<change>/   an archived change, unchanged
```

`init` creates this. `AGENTS.md` is a hybrid: the bytes between the
`<!-- specd:begin … -->` and `<!-- specd:end -->` markers are harness-owned and
regenerated by `init`, and anything you write outside them is preserved.

Commit all of it except the lock files, which the managed
`.gitignore` already excludes — the whole point is that the plan travels with
the code, in review, in the same pull request.

## Ownership

| you author | the harness owns |
| --- | --- |
| `proposal.md` | `state.json` |
| `design.md` | `history.jsonl` |
| `tasks.md` | `evidence.jsonl` |
| `changes/*/specs/*/spec.md` | `specs/*/spec.md` (written by `sync`) |
| | everything under `archive/` |
| | the lock files |

Hand-editing anything in the right-hand column is not "advanced usage". State
is written atomically under a revision guard, records are append-only with
replay, approvals are content hashes, and evidence is pinned to a Git HEAD.
Editing them by hand either gets refused as corrupt or silently breaks the
guarantee the file exists to provide. There is no task-marker checkbox to tick:
task activity lives in `state.json`, not in `tasks.md`.

If a file in that column is wrong, the fix is an operation, or repair outside
automated mutation — which is exactly what the refusal will tell you.

## Naming

Change and capability names are lowercase kebab-case: `add-dark-mode`, `accounts`,
`release-qualification`. Six segment names are reserved because the managed tree
uses them: `archive`, `changes`, `evidence`, `history`, `specs`, `state`.

A change name must be unique against both active changes *and* the archive, so
you cannot resurrect a name that already has history. Archived directories are
prefixed with the local calendar date they were archived on.

Path resolution refuses escapes and refuses every symlink in an existing prefix.
A managed write target that resolves outside `.specd/` is a `path_escape`
refusal, not a clamp.

## `state.json`

```json
{
  "schemaVersion": 1,
  "change": "add-dark-mode",
  "stage": "planning",
  "condition": "active",
  "revision": 1,
  "approvals": [],
  "tasks": {},
  "createdBy": "fa4858a7…",
  "lastTransition": "fa4858a7…"
}
```

| field | meaning |
| --- | --- |
| `schemaVersion` | exactly `1`; a future version fails closed rather than guessing |
| `change` | must match the directory name, or the state is an identity mismatch |
| `stage` | `planning`, `approved`, `executing`, `reconciling`, `archived` |
| `condition` | `active` |
| `revision` | monotonic; the value `start`, `complete`, and `friction` guard against with `--revision` |
| `approvals` | recorded approvals, each with per-artifact hashes and an aggregate hash |
| `tasks` | task id → persisted activity |
| `createdBy`, `lastTransition` | the record ids that produced this state |

Writes are old-or-new: a crashed write leaves the previous bytes, never a
half-file. A write against a revision that has moved is refused, not merged.

## The two ledgers

Both are JSON Lines, append-only, replayed on read, and interrupted appends are
recovered rather than trusted.

`history.jsonl` — one line per lifecycle transition:

```json
{"schema_version":1,"id":"fa4858a7…","family":"history","kind":"created",
 "change":"add-dark-mode","expected_revision":0,"resulting_revision":1,
 "timestamp":"2026-07-31T15:54:43.980692264Z","actor":"xkhdr","payload":{}}
```

History kinds: `created`, `approved`, `task_transition`, `attempt`,
`completion`, `synced`, `archived`, `friction`.

`evidence.jsonl` — one kind, `observed`: a verification run recorded with its
command digest, start and end times, exit code, pass flag, timeout and
interrupt flags, non-vacuous and zero-match flags, and bounded output digests
and excerpts.

Two flags there matter more than they look. **Non-vacuous** means the run
actually asserted something; a test command that matched zero tests passed
without proving anything, and `zero_match` records that. Evidence that proves
nothing does not complete a task.

## Where things get read from

- `check` reads the four authored artifacts and reports gate findings.
- `approve` hashes the covered artifacts and stores the aggregate. Change a
  byte afterwards and the approval is stale.
- `next` and `status` derive readiness from `tasks.md` plus `state.json` —
  nothing about readiness is stored.
- `context` assembles bounded read input for one task and refuses if the
  required inputs exceed `--budget-bytes`; optional inputs are dropped first
  and the omission is recorded rather than hidden.
- `verify` writes to `evidence.jsonl` only.
- `complete` reads applicable evidence and writes `state.json` and
  `history.jsonl` in one guarded transaction.
- `sync` writes `specs/` and the change state as one transaction: every file or
  none.
- `archive` moves the change directory and refuses a target collision.
- `report` and `review` without `--verdict` only project existing facts.
  `review --verdict` records a separate review; neither form authorizes a human
  gate or changes accepted behavior.

## Version control

Commit `.specd/` with your code. The plan, its approval, the evidence trail,
and the accepted specs are meant to be reviewable in the same diff as the
implementation — that is most of the value of keeping them in Markdown and JSON
Lines instead of a database.

Commit after each completed task before starting another. A clean baseline
keeps each task's declared scope and evidence attributable to that task alone.

Merge conflicts in `history.jsonl` or `evidence.jsonl` mean two branches
recorded history against the same root. Resolve by keeping both sides' lines;
they are append-only and each line stands alone.
